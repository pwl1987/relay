# Relay Agent 控制与本地质量契约（架构版本 1）

状态：**FROZEN（原则与禁止事项）/ OPEN（新增实现、操作协议字段及验收阈值）**。
本文件是 ARCHITECTURE_BASELINE.md 所引用的专项契约；不得成为第二套项目状态或执行授权。
依据：AGENTS.md、CONTRACTS.md、docs/DELIVERY.md、docs/VALIDATION_PLAN.md、ADR/0003、0004、0007、0008、0009。审计起点：51972cdeb89a（2026-11-13）。
**注意：架构冻结不表示相应功能已实现。** 现有工作流与 Gate 的真实成熟度仍以 live main 代码和验证证据为准。

## 1. 产品目标与最小拓扑

Relay 的定位是受控的自主软件交付负责人，而非多 Agent 聊天平台。用户提出目标、查看可核实进度、必要时干预/接管、验收成果。
唯一持久工作流/计划/任务/许可/验收权威是 Relay Core + PostgreSQL；唯一远端项目事实源是 GitHub main。
Pi 是首个 Agent 执行 Runtime；Pi 子 Agent、Session、MCP、Skill 和 Extension 均不能取代 Relay 权威。
部署默认继续使用现有 Server、Worker、PostgreSQL 和按需 Pi 子进程；不为逻辑分层新增常驻调度服务、消息总线或独立质量服务器。
模块、进程数量、物理主机可演化，但不能新增重复真相源。GitHub Issue 只跟踪任务，不能直接调度 Run。

## 2. 工作对象及所有权

- Project：逻辑项目及授权仓库；Project 不等于物理仓库。
- Goal：用户意图、验收目标、授权边界与当前业务状态；聊天内容不等于执行授权。
- PlanRevision：目标的不可变计划版本，记录原因、输入事实、受影响 Task 和新旧版本；先复用现有 Goal/Task/Audit 结构，未验证前不承诺新表。
- Task：有界的可调度工作项，包含依赖、验收、预算、权限和计划版本；禁止没有有效 Goal/Plan 的可写 Task。
- Run：某 Task 的一次执行尝试，绑定 Pi 版本、模型、输入 commit、沙箱、租约、审计和实际资源。
- Agent：用户可识别的执行身份/角色；独立于操作系统 PID，不把进程当持久任务事实。先以 Task/Run 映射视图表达，新增 Registry 必须有需求证据。
- Pi Session：一次或多次交互的上下文实体，非工作流权威；P0 仍为无会话持久化的短 Run，交互式重入需专项 POC。
- Web 登录会话、Agent 输入控制会话与 Pi 上下文 Session 分属不同信任面，不得复用同一个会话 ID 或把登录态当作任务执行资格。
- ControlCommand：用户对特定 Goal/Task/Run 的查看、指导、暂停、终止、接管、交还指令，带操作者、目标版本、幂等 ID、权限与回执。
- Evidence：来自确定性执行器的构建、测试、工具、Reviewer 与交付事实，绑定输入版本、代码 SHA、环境和时间。

## 3. 用户输入语义与执行授权

用户输入区分：只读咨询、需求探索、创建目标、补充方向、修改计划、操作控制、批准或拒绝高风险动作。
对普通对话不得默认创建 READY Task；创建、追加、重开或改变可写任务必须经过明确意图及权限检查。
终态 Goal 上的新要求不得静默派生可执行 Task；应生成关联新 Goal 或经可审计授权重开，并保持旧验收历史。
网络超时后重发相同控制命令不得重复生效；重复自然语言消息也需业务级幂等/确认机制。
命令文本和网页/仓库内容均是不可信输入，不可通过提示词改变 Policy、审批级别或资源上限。

## 4. 会话观察、指导、停止与接管

观察：显示真实运行事件、可见 Pi 消息、工具调用和结果；会话离线时显示最后可核实状态，不伪造“正在思考”。
指导：向指定在途 Run 发送 steer/下一步请求；收到 RPC ACK 只表示命令被接收，不能声称旧操作已中止。
暂停：先阻止旧计划领取后续可写任务，再选择安全停点或受控终止。当前 READY→PAUSED 不能冒充在途暂停。
紧急停止：立即撤销后续执行资格，终止可控制的 Pi 子进程及工具组，对未知外部副作用先 Reconcile。
人工接管：必须在 Core 内撤销原 Writer 资格、阻止旧 Run 推进、核查正在执行的动作，再把受控写权限交给用户。
交还 AI：核对人工修改的 Git 状态、计划版本、测试证据和权限，再授权新 Run。人工对话指导本身不授予额外写权限。
一人多个浏览器标签可同时观察；同一 Task/受控工作区同一时刻只能有一个有效输入/写入控制者。

命令回执语义至少区分：RECEIVED（系统接受）、QUEUED（待安全边界）、APPLIED（执行端确认生效）、STOP_CONFIRMED（旧执行资格已失效且有证据）、FAILED/REJECTED/EXPIRED。
需要持久审计命令发起者、目标、计划版本、控制权版本、预期 Task 状态、结果及实际生效时间。
控制命令断网重试时不可越过当前版本，旧回执不得被新客户端误显示为本次成功。

## 5. 方向纠偏与计划版本

模型可提出“方向可能错误”的证据、备选方案和最小实验，不能擅自改变用户授权的业务目标与风险预算。
PlanRevision 生效前先标记旧计划不再可领取，拒绝旧 fencing/version 的后续写入或状态推进。
已存在的候选 Diff、测试与审查保留并标注来源；旧证据不可自动用于新方案或新提交。
改动范围、预算、权限、目标仓库、不可逆操作升级须得到对应授权，不得借重规划隐式扩权。
“执行错方向”和“代码有缺陷”不能都按普通重试处理：同因连续失败需触发根因诊断与重新规划。
交付事务跨 GitHub/SSH/数据库不承诺 exactly-once；未知结果先核对，不能盲回放或删除现场。

## 6. 多 Agent 及资源边界

Relay Core 决定任务分配、依赖、并发、优先级、验收和全局预算；Pi 可在获得的 Task 范围内使用局部子 Agent。
只有 Relay 授权的工具和作用域能产生外部副作用；子 Agent 权限必须是父任务权限的子集，不能自行扩大。
允许并行只读调查、设计候选、独立复核；同一真实仓库仍只有一个可写 Writer，严禁创建其他 Git 分支；确有隔离需求只能采用允许的 detached 临时工作区或独立临时目录。
父任务取消、权限回收、租约过期必须可传播到所有受影响子进程，并验证进程组及外部副作用。
子 Agent 消耗计入父 Goal/Task 的整体预算；失败、重试、挂起、调用开销也应有可追溯记录。
隔离 Reviewer 必须有独立执行上下文和可靠 Diff/测试证据，不能仅由 Coder 自报或复述模型结论。

## 7. Pi、pstack 和生态升级

生产 Pi 固定精确版本，禁止使用自动漂移的全局 Pi；上游升级经候选验证、隔离测试、回滚计划和显式放行。
优先复用 Pi 的 steer、abort、Session、Compaction、Skills、MCP 与 Extensions；Relay 仅补业务控制和安全桥接。
扩展可运行任意代码，工具 allowlist 不等于扩展可信；须检查版本、许可证、网络、容器挂载、子进程和权限。
pstack 的需求质疑、反例审查、简化设计、TDD 等方法可选复用；其子 Agent 调度、Loop、自动建分支及持久任务机制不能取代 Relay Core。
不默认全量注入 Skills/工具列表；按任务渐进加载并记录 Token、请求数、工具输出和有效交付率。
不得使用额外常驻摘要模型替代 Pi 原生 Compaction；需要时以受控 A/B 实验证明成本与质量收益。

## 8. 本地优先的统一质量工作流

本地与 GitHub 云端使用同一版本锁定的检查脚本/配置；本地可以独立验证，GitHub Actions 作为外部交叉确认。
推荐三个逻辑入口：quality:quick（格式只检、Lint、类型、相关单测）；quality:full（全范围相关单元/集成/浏览器/Reviewer）；quality:release（安全、性能、权限与真实环境专项）。
入口尚未实现，工具初选 Biome 或经证据确认的单一格式/Lint 工具；不同时堆叠功能重复的多套工具。
本地 Runner 使用独立沙箱和 DB/schema，固定依赖、最小权限、资源限额、超时和测试产物清理；不能碰生产数据库、凭据或 Docker Socket。
不得为公开仓库直接在生产 VM80 宿主注册长期驻留的 GitHub 自托管 Runner；除非隔离和安全风险另有明确裁决。
云端 CI 额度不足、服务不可用或跳过真实模型门时，可继续已授权的本地操作；但不得伪称云端验证成功或远端已交付。
GitHub 推送 main 后 CI 失败时，明确显示已推送但未通过交付验证；保持前进式修复/必要时受控回滚，不自动强推或改写 Git 历史。
依赖及 GitHub Actions 引用应锁定可验证版本，必要时固定不可变提交；工作流最小权限，测试报告不含敏感数据。
工具执行为确定性规则，模型不能决定“忽略必需测试”或修改既有 Gate 门槛。

## 9. 最低机器证据和审查评价

每个有代码变更的候选必须具备按影响面确定的机器证据集合（构建/类型、必要单测、接口集成、UI 真实旅程等）。
任一必需检查 FAILED、SKIPPED、NOT_RUN、证据缺失、版本不匹配，必须阻断该变更的 ACCEPTED；不适用的检查需有确定性规则与可审计理由。
独立 Reviewer 的自然语言判断和 reviewer_output 证据不得独自满足代码变更的最低测试证据要求。
变更了权限、租约、状态、恢复、交付、凭据或网络时增加安全与故障注入；涉及用户界面时增加真实浏览器交互；涉及性能时进行同环境回归。
自动格式化只发生在受控候选工作区；正式 Gate 做只读检查，避免不经确认直接格式化原始大仓库。
复杂度、可维护性、重复代码和依赖数量作为多维评价；不能用代码行数或未校准的单一评分直接批准/拒绝交付。
先证明正确、安全、可恢复，再比较代码量、Token 与运行时间；不把减少 Token 当成功率下降的借口。

## 10. 性能与效率

按变更风险选择性能测试；首次测量提供硬件、负载、版本、配置和冷/热状态，不倒填阈值。
重点关注任务领取延迟、用户控制生效时延、失败恢复时延、API p95、数据库负载、模型调用与 Token、返工率和有效交付。
性能判定采用可比基线和多次样本；有共享 GPU/CPU 干扰时记录并拒绝虚假结论。
不把 24h 空闲进程连续性等同于实际模型工作负载下的可靠性；原 R-3 PARTIAL 历史不改。
安全与功能硬门不可由更快速度、更低 Token 或更高代码质量评分抵消。

## 11. 确定性与模型职责

程序决定：命令目标和权限、预算、Lease/Fencing、依赖、PlanRevision 生效、幂等、状态、验收证据、重试次数、告警与执行。
模型负责：理解模糊需求、质疑前提、调查与规划、代码设计、复杂原因推断、提出可反驳建议。
模型提出的判断不得直接成为 Policy 授权、必需 Gate 放行、不可逆操作的审批或 GitHub 最终交付事实。
模型不可用时仍可安全完成已授权的确定性维护、状态核对和可执行的非模型任务，不得为了保持“活跃”无限自问自答。

## 12. 架构冻结与实施验收边界

已冻结：Relay Core 唯一权威、Pi First、单 Writer、受控人工接管、多 Agent 权限原则、机器质量门、本地可独立运行的统一 CI、最小必要复杂度。
未验证/待实施：会话实时重入与接管协议、计划修订数据落地、子 Agent 进程管理、质量脚本、风险分级机器证据约束、性能阈值、pstack 适配。
新增功能需先按受控 WorkPackage 在隔离环境实施并经过独立 Reviewer、真实测试和明确用户验收；本设计不自动激活新开发包。
发现与现有冻结 ADR 相冲突的实现必须先提 ADR 修订，不得仅改代码隐式改变安全不变量。
