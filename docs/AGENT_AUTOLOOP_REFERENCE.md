## 结论摘要

六项重点(A–F)判定一览:**A 已覆盖=NO-CHANGE;B 候选(P1-1);C 候选(Architecture invariant 先行,P1-2);D 已覆盖=NO-CHANGE(hop/provenance depth=Later);E Source=候选(并入 P1-2);E' Channel=候选(P1-3);F 部分缺口(NEEDS_RECONCILE 生产不自愈缺口如实纳入;补跑语义待 Source 接入后随 C/E 设计)**。五项明确拒绝全部维持 REJECT:事件溯源内核、改 SQLite、第二 Rules Scheduler、复制 Delivery Pipeline、autoloop 作 Relay↔Pi 必需中间控制器。autoloop 与 Relay 在"暂停零消耗、回执协议、预算/退避/熔断、append-only 事实"四个面上已是同构设计,无迁移价值;真正的增量价值在 **B(因果链可解释性投影)** 与 **C/E(外部 Source 接入前的信任边界 invariant)**。

## 借鉴后优先级建议(P1 候选排序;**最终以独立 Reviewer 结果为准**)

1. **P1-1 Explain/Why 因果链投影**(B 行,候选):新增只读投影层(仿 `src/server/views/goal.ts:641-760` Goal Feed 模式),从既有 audit_events/tasks/runs/decisions/task_gate_verdicts/intents/delivery/gate 消费事实生成 Task/Goal 级时间线;零新状态、零生命周期变更;价值=把"NEEDS_DECISION 为什么停在这/这轮经历了什么"从运维查询变成用户可读,是后续所有外部接入可观测性的地基。
2. **P1-2 外部 Source 安全边界 = Architecture invariant**(C+E 行,候选/invariant 先行):先写 invariant 文档+对抗性测试(事件字段白名单、执行面字段拒收留审计、外部文字只进资料工件、Source 只翻译不执行、per-source 最小能力、回调只经 ops 授权路径),作为未来 GitHub Issue Source / Webhook / Cron / Search·Crawler 的准入门槛;实现层随后续 Source 工作包,不提前建插件运行时。
3. **P1-3 Channel/Notification 轻量投递**(E' 行,候选):Decision/Goal Feed → 外部通知(飞书/手机推送)worker;控制面仍 Relay Decision 唯一裁决,回答回流走 resolveDecision 授权;先通知后双向。
4. **P1-4 Pause/Resume/Replay 完善**(F 行,部分缺口):最高优先的实为 Relay 自身生产缺口——**NEEDS_RECONCILE 自愈(worker-entry supervisor 环路无 executor)**,属修复项而非借鉴项,建议与 1 并行;pause `until`/skipped 证据/replay 补跑语义待 P1-2 Source 落地后一并设计。
- **Later(DEFER)**:hop/provenance depth——仅当 Relay 未来引入"Agent 可发事件"能力时再评估轻量字段,现在不加机制。
- **Reject(终局)**:第二事件溯源 Core(PG+Lifecycle+Audit 已是 SoT)、改 SQLite、第二 Rules Scheduler/Engine(Goal Loop/Policy 已存在)、第二 Delivery Engine(Gate/Intent/GitHub Delivery 已存在)、autoloop 作 Relay↔Pi 必需控制器(双控制平面)。
